# Temporal / NATS 与 OPIC 能力中心的集成说明

> 本文件回答一个问题：**这两个组件在 OPIC 本体体系里处于什么位置，哪些事能做、哪些不能做。**
> 需求侧依据：23 域需求基线 **v3.2** ＋ **v3.3 承接补齐**（见 `opic-ontology/output/112-评估-Temporal与NATS归属及techbase更新.md`）。

---

## 一、定位：第 3 层可替换实现，不是能力中心

两个组件**都不新建能力中心**，均归 **`O-SYS` 平台底座域**，属**第 3 层（可替换实现）**。

| 组件 | 承担的能力 | 语义归属（第 2 层） | 判据 |
|---|---|---|---|
| **NATS**（JetStream） | 事件传输与持久化重放 | `O-SYS` **事件总线**：`EventType`（§2.7）/ `EventSubscription`（§2.8）/ `INV-20`·`22`·`23`·`24` / `B-AUTO-03` 投递 / `PROC-05` 死信处置 | 替换传输实现**不触发任何本体对象 / 不变量 / 规则变更** → 实现级 |
| **Temporal** | 流程引擎运行 / 工作流编排运行时 | `O-SYS` **流程引擎运行**（C5 ＋ §1.6.3 ＋ §1.6.1 第 7 行）｜`O-APP` **编排结构语义**（`WorkflowDefinition` / `INV-45`·`47` / `R-16` / `PROC-08`） | 编排结构语义已建模；**执行本体在域外**（`O-APP` 显式声明）→ 实现级 |

> **判据出处**：《00-总体规划-OPIC本体化重构》**附录 A** 表头 —— 「若替换某组件**不触发任何本体对象 / 不变量 / 规则变更**，则该组件属实现级（第 3 层）；若其行为语义已被某域建模，则语义归属在该域（第 2 层）」。

**为什么不成域**：`O-SYS` §1.3 已裁定「**只有『有身份、有生命周期、需被引用』的实体才建对象**；网关、审计管道这类**执行器**不建对象」。消息中间件与工作流引擎都是**执行器** —— 它们的行为应在 `O-SYS` 以 `B-AUTO-*` / `R` 表达，而非新建域。

## 二、职责切分（一句话版）

```
O-SYS 定义「事件长什么样、谁能订阅、投递失败怎么办」   ← 语义权威（第 2 层）
NATS  只负责「把事件送过去」                          ← 实现（第 3 层）

O-APP 定义「这张流程图合不合法」                       ← 语义权威（第 2 层）
O-SYS 承载「把这张图跑起来」                          ← 运行归属（第 2 层声明）
Temporal 负责「真的跑起来」                           ← 实现（第 3 层）
```

- **事件编目与订阅关系**：`O-SYS` 的 `EventType` / `EventSubscription` 是权威源。NATS 的 stream / subject 是它们的**投影**，不是定义处。
- **工作流的结构合法性**：`O-APP` 的 `INV-45`（图无环连通）/ `INV-47`（人审不可绕过）/ `R-16`（工具绑定须 `active`）判定。Temporal 只执行，**不拥有判定权**。
- **执行明细**：归 `O-MON`（`O-APP` 明确「执行明细不落本域」）。Temporal 自带的 Web UI / 事件历史**不能替代 `O-MON` 的观测口径**，须导出为 `O-MON` 可采集的指标与日志。

## 三、四条硬边界（越界即违反基线纪律）

| # | 边界 | 依据 | 反例（禁止） |
|---|---|---|---|
| 1 | **消息中间件不得作平台状态存储** | C3「禁止共享数据库表」＋ 判据 1「真相位置显式化」 | 用 JetStream 的 KeyValue / ObjectStore 存业务状态 → 形成**第三个真相源** |
| 2 | **同步契约仍走统一网关** | `O-SYS` `CallAuditRecord` 记的是「**经网关的**中心间调用」 | 域间同步调用改走 NATS 请求-响应 → **绕开审计** |
| 3 | **消费方必须幂等** | `B-AUTO-03` 为 **at-least-once**（Q-12）＋ 超限留痕与**人工重放**（Q-19） | 重放导致重复入账；与「账本只增不改」（`O-CSC.INV-27` / `O-OPR.INV-08` / `O-CMP.INV-04`）冲突 |
| 4 | **工作流活动的自动重试必须幂等** | 同上（Temporal 的 Activity 重试是内建行为） | 重试导致重复副作用写入 |

> **边界 3 的补充**：`PROC-05` 规定投递失败「**不自动丢弃、不无限重试**」，由 `SYS-ROLE-04` 事件订阅管理员**逐条或批量重放**。这意味着重复投递是**设计内**的正常情况，而不是异常 —— 消费侧必须按业务编号 / 幂等键去重。

## 四、命名与主题规划（建议，建模期定稿）

`O-SYS` 现有的事件编码形如 **`sys.center.changed`**（`B-AUTO-05`）—— 已是**小写点分**形式，与 NATS 的 subject 天然契合。建议：

| 项 | 建议 | 说明 |
|---|---|---|
| subject 形态 | `opic.<域码小写>.<事件名>` | 如 `opic.sys.center.changed`；域码取 23 域登记表 |
| stream 划分 | 按**保留策略**划分，而非按域 | 例如 `OPIC_EVENTS`（Limits，常规事件）/ `OPIC_WORKQUEUE`（WorkQueue，任务分发） |
| consumer 命名 | `<订阅方中心码>-<用途>` | 对应 `EventSubscription.subscriberCenterCode`，便于与域内台账对账 |
| 是否预建 stream | **否** —— 由建模期按 `EventType` 编目结果创建 | 本仓库刻意不预建，避免部署脚本成为第二份事件定义 |

> **Temporal 命名空间**：`default` 保留给运维自用，OPIC 业务使用 `.env` 的 `TEMPORAL_NAMESPACE`（默认 `opic`）。
> Task Queue 建议按域划分（如 `opic-app-workflow`），与 `O-APP` 的编排定义一一对应。

## 五、与 opic-techbase 的对接点

应用侧（`opic-techbase`）**不应直连** NATS / Temporal 的客户端库，而应经**接口层**调用：

| 能力 | 接口层位置（建议） | 默认实现 | 外部实现 |
|---|---|---|---|
| 事件发布 / 订阅 | `internal/pkg/eventbus`（接口 + 双实现） | 进程内（零依赖，开箱即跑） | NATS（本 stack） |
| 工作流执行 | `internal/pkg/workflow`（接口 + 双实现） | 自研轻量引擎（现 `service/engine/flow_engine.go`） | Temporal（本 stack） |

**理由**：① 保持脚手架「`cp -r` 即可运行」的轻量特性；② 中间件不可用时业务系统仍能降级运行；③ 与「第 3 层可替换」纪律一致 —— 换实现不改上层代码。
