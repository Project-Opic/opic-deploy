## 一、一句话结论

**NATS 与 Temporal 相互无依赖，可并行；但推荐 `NATS → Temporal`，位置固定在「`O-SYS` 语义层之后、业务能力中心之前」。**

三条理由：① 两者是**第 3 层实现**（执行器），语义契约在 `O-SYS`，**权威必须先于实现**；② NATS **零外部依赖**（无库、无磁盘前置），是最快的可验证单元，符合"零依赖先起"；③ Temporal **依赖 PostgreSQL**（数据面），启动链更长、排障面更大，后置便于单独定位。

## 二、排序判据（J1~J7）

> 判据是本文的"专家理由"骨架。每条排序决策都必须能落到其中至少一条；落不到，就不该出现在顺序表里。

| 编号 | 判据 | 说明 | 依据 |
|:--:|---|---|---|
| **J1** | **拓扑序优先** | 有向依赖图必须按拓扑序部署：A 的运行依赖 B 已可用 ⇒ B 先。这是硬约束，不可协商 | E-01 E-02 |
| **J2** | **权威先于实现** | 语义权威（本体能力层）先于第 3 层实现；否则实现层无契约可依（第 3 层可替换，换的是实现不是语义） | L-06 L-07 |
| **J3** | **面分离：数据面先、控制面后** | 同一个域可拆两面 —— **数据面**（实例／存储／采集代理）无业务依赖，先起；**控制面**（供给／治理／注册／编排）依赖身份与注册，后起 | E-04 L-03 |
| **J4** | **零依赖先起、重依赖后置** | 无依赖栈先起，快速暴露基础问题；依赖最多的后起，故障时变更面最小 | E-02 |
| **J5** | **横切两段式：观测早准备、晚收口** | 采集侧（exporter／agent）随基座起；聚合与告警（中心本体）最后收口。若全部后置，前序阶段全是"盲飞" | E-04 |
| **J6** | **幂等优先：先可逆、后可见** | 先做幂等可重入的动作（生成密钥、建目录、导入镜像），后做产生外部可见状态的（对外域名、注册元数据） | E-03 L-01 |
| **J7** | **档位分层：minimal → standard → full** | 每档是独立可交付里程碑；先立最小可用集合，验证通过再叠加 | L-02 |

## 三、部署顺序总表

> **启动正序执行；停止、升级、回滚一律逆序。**

### Ⅰ 平台前置（S0~S3）

| 序 | 部署对象 | 前置 | 承判据 | 理由（要点） |
|:--:|---|---|:--:|---|
| **S0** | 主机与运行时：Docker Engine 24+ / Compose v2、`yq`、`opic-net` 容器网络、数据目录、`/etc/hosts`、时钟同步 | — | J1 J4 J6 | 全部 stack 的运行时前提；网络须**先于任何 `docker compose up`** 存在（compose 引用的 `opic-net` 为 external）。**零依赖，最先起，故障最先暴露** |
| **S1** | 凭据与密钥：生成 `POSTGRES_ADMIN_PASSWORD` / `JWT_SECRET` / `NATS_PASSWORD` / `TEMPORAL_PG_PASSWORD` 等，落 `.env.runtime`（权限 600） | S0 | J6 | 必须在任何 compose 之前完成 —— 密钥确定后 `derive_env` 重算派生变量，装到一半再生成会导致先起的容器拿旧口令。**幂等动作先做**（可重复执行、不产生外部可见状态） |
| **S2** | 宿主初始化：`init-volumes` → `init-hosts` → `init-certs` → `init-nfs` | S1 | J6 J5 | 目录权限与挂载点必须先于容器绑定挂载存在，否则容器以 root 建目录、宿主侧权限错乱。**采集侧 exporter 亦在此挂载宿主目录**（J5 的前半段） |
| **S3** | 镜像准备：离线导入（`load-images`）或在线拉取 | S0 | J4 J6 | 离线环境下载入失败要尽早暴露（体积大、耗时长）；在线模式由 compose 拉起时自动拉取，此步退化为校验 |

### Ⅱ 数据与身份地基（S4~S5）

| 序 | 部署对象 | 前置 | 承判据 | 理由（要点） |
|:--:|---|---|:--:|---|
| **S4** | **数据基座**：PostgreSQL 16 实例（OPIC 统一口径 `opicdb`）、NFS 共享存储 | S2 S3 | J1 J3 J4 | **数据面先于应用面**：所有需要持久化的服务（`O-SEC`／`O-SYS`／`O-ARC`／`O-DBS`）都在其后。实例本身**不含业务语义**，因此可在身份中心之前起（这是 J3 的关键应用，见 §4.1）。注意：数据落 **NVMe/本地 SSD**，勿放 NFS（JetStream 与 PG 的随机写会被显著拖慢） |
| **S5** | **`O-SEC` 零信任安全域**：ZITADEL（OAuth2/OIDC）＋ 其数据库 | S4 | J1 J2 J4 | **全平台唯一登录入口**，被 22 个域依赖 ⇒ 必须最先具备完整语义的中心。同时是 ZITADEL → `O-SYS` Casbin 授权链的源头（授权判定优先 Casbin、回退 ZITADEL） |

### Ⅲ 语义层与第 3 层实现（S6~S8）

| 序 | 部署对象 | 前置 | 承判据 | 理由（要点） |
|:--:|---|---|:--:|---|
| **S6** | **`O-SYS` 平台底座域**：能力注册发现、RBAC、配置、审计、网关、**事件总线语义** | S5 | J1 J2 | 其余 22 个域都要在它这里注册能力、取配置、走网关、落审计。**语义权威**：`EventType`／`EventSubscription`／`CallAuditRecord` 的定义在此 |
| **S7** | **`O-ARC` 架构元数据域**：统一错误码／元数据注册与 SDK 分发 | S5 S6 | J1 J2 | 与 `O-SYS` **契约强耦合**（旧仓即以单 stack `arch-day0` 共同承载）。放同阶段、略后即可 |
| **S8** | **第 3 层中间件实现**：**① NATS（事件总线实现）→ ② Temporal（流程引擎运行实现）** | S6 | J1 J2 J4 | **本文的核心结论**，论证见 §4.2 |

### Ⅳ 基础设施型中心（S9~S10）

| 序 | 部署对象 | 前置 | 承判据 | 理由（要点） |
|:--:|---|---|:--:|---|
| **S9** | `O-REG` 制品仓库域（镜像／Helm）／`O-CRT` 证书信任域（PKI）／`O-VPN` 网络连通域 | S5 | J1 J2 | **为后续中心提供交付物与通道**：`O-REG` 是后续中心的镜像来源（离线部署时由 S3 导入兜底，故不阻塞）；`O-VPN` 提供跨机 overlay（单机形态可后置）；`O-CRT` 提供 PKI（若 TLS 用外部／自签证书则可后置，属**条件依赖**） |
| **S10** | **`O-DBS` 数据服务域**（控制面）：实例供给、连接凭据、备份与高可用 | S4 S5 | J1 J3 | **控制面后于数据面**：S4 已把 PG **实例**拉起，此处起的是"供给与治理"的控制面 —— 建库、发凭据、定备份策略，均需先有身份（S5）与注册（S6）。**顺序上必须区分 S4 与 S10，二者不是同一件事** |

### Ⅴ 交付与集群使能（S11~S12）

| 序 | 部署对象 | 前置 | 承判据 | 理由（要点） |
|:--:|---|---|:--:|---|
| **S11** | `O-IGN` 交付执行域 → `O-CLC` 集群域 → `O-OSC` 节点使能域 → `O-ADD` 集群扩展域 | S7 S9 S10 | J1 J2 | 严格遵循总纲 §四 **B4 批**的链式依赖：`点火` 调度执行机 → `集群` 声明与编排 → `节点使能`／`扩展组件` 分发到集群。**链内不可乱序**（后者的输入是前者的产物） |
| **S12** | `O-AST` 资产域：节点资产台账、接入装配、巡检与漂移 | S7 S11 | J1 | 资产是集群的**前置台账**，但其"接入装配"动作需要交付链（S11）已具备执行能力 |

### Ⅵ 业务与智能层（S13~S16）

| 序 | 部署对象 | 前置 | 承判据 | 理由（要点） |
|:--:|---|---|:--:|---|
| **S13** | `O-USR` 租户门户域 → `O-PIP` 流水线域 → `O-APP` 应用域 → `O-CSC` 算力调度域 | S5 S6 S11 | J1 J2 | Tier 2 起点（总纲 §四 **B5 批**）。`O-PIP` 产出的制品进 `O-REG`（S9），`O-APP` 部署的应用需要 `O-CSC` 的算力单元，故链内按此序 |
| **S14** | `O-APF` 接口与令牌域 → `O-OPR` 运营成本域 | S13 | J1 | **南北向流量收口**（总纲 §四 **B6 批**）：`O-APF` 要做路由与消费计量，**被计量的东西必须先存在**；`O-OPR` 采集的是已发生流量与算力消耗的成本 |
| **S15** | `O-DAT` 数据资产域 → `O-MDL` 模型域 → `O-KNB` 知识库域 | S13 | J1 | 总纲 §四 **B7 批**：知识库依赖数据集与嵌入模型，链内按序。三域是 v1.1 扩域批次，属**可选档位**（见 §6） |
| **S16** | **`O-CMP` 内容合规域**：内容审核、生成内容标识、算法／模型备案台账 | S13 S15 | J1 | **上线前置合规闸门**：审核的对象（应用产出内容、模型）必须先存在。故排在业务与智能层之后、对外放量之前 |

### Ⅶ 横切收口（S17）

| 序 | 部署对象 | 前置 | 承判据 | 理由（要点） |
|:--:|---|---|:--:|---|
| **S17** | **`O-MON` 可观测域（聚合面）**：Prometheus／Grafana／告警规则 ＋ 全量验证（`verify`） | 全部 | J5 J1 | **收口侧**：采集侧已在 S2／S4 随基座起来，此处补的是"聚合、规则与通知"。最后收口的原因：**它依赖的东西最多**（J4）—— 且验证脚本需要全部服务在线才有意义 |

## 四、两处关键论证

### 4.1 为什么"数据基座（S4）"排在"数据服务域 `O-DBS`（S10）"之前

这是本文最容易被误读的一处 —— 表面上"数据库中心"应当最先，实际不是。

| 视角 | 结论 |
|---|---|
| **数据面 / 控制面** | S4 起的是**实例**（一个 PG 进程 + 卷），**不含任何 OPIC 业务语义**；S10 起的是**域本体**（实例供给、凭据签发、备份策略），需要身份（S5）与注册（S6）才能工作 |
| **依赖方向** | `O-SEC` → 需要 PG ⇒ PG 必须先于 SEC。若把 `O-DBS` **域本体**提到 S5 之前，它自己反而要等 `O-SEC`（登录）与 `O-SYS`（注册）—— 会形成**互相等待** |
| **判据** | J3（面分离）＋ J1（拓扑序）。把"实例"与"治理"当作两个部署单元，矛盾即解 |

**推论（需注意的不一致）**：`O-SYS` 的 DB 纪律是"统一 `opicdb`，按 schema 前缀隔离"。当前 `stacks/temporal` **自带一个 PG 实例**（为便于独立起停）。这与统一口径存在张力：Temporal 官方需要独立库（`temporal` / `temporal_visibility`）且 `auto-setup` 自动管 schema，若改指向共享实例需先由 `O-DBS` 授权建库。**两条路都成立**：① 保持独立实例（当前实现，运维简单）；② 接入统一实例（更贴合纪律，需 `O-DBS` 提供库与凭据）。**建议：保留当前独立实例，但把"是否并库"作为 `O-DBS` 域的一个决策点登记**。

### 4.2 NATS / Temporal 的定位论证（本文核心）

| 问题 | 结论 | 理由 |
|---|---|---|
| 为什么**不最早**（不先于 `O-SYS`） | ❌ | 两者是**执行器**：NATS 只是"管子"、Temporal 只是"运行器"。OPIC 的判据明确"**只有『有身份、有生命周期、需被引用』的实体才建对象；网关、审计管道这类执行器不建对象**"（L-06）。**语义权威（`EventType`／`EventSubscription`／`WorkflowDefinition`）在 `O-SYS` 与 `O-APP`** ⇒ 权威先于实现（J2） |
| 为什么**不最晚**（不晚于业务中心） | ❌ | `C3` 禁止共享表，跨中心协同只能走 **HTTP API ＋ Event Bus**；业务链（`O-IGN`→`O-CLC`、`O-CSC` 审批流）依赖事件投递与流程编排。若晚于业务中心，业务中心上线即"**协同断链**" |
| 为什么 **NATS 先于 Temporal** | ✅ | ① **NATS 零外部依赖**（无库、无额外卷），最快可验证（J4）；② 语义上**通道先于编排**：Temporal 编排出的跨中心步骤要靠事件总线投递，通道是编排的承载；③ Temporal 依赖 PG，**启动链更长**（PG healthy → schema 迁移 → SERVING → 建 namespace），后置便于单独排障 |
| 两者能否**并行** | ✅ 可以 | 二者无相互依赖，`.env` 与 compose 互不引用。**顺序是"推荐序"，不是"硬依赖"** |
| **缺失是否阻塞** | ❌ 不阻塞 | 接口层默认回落到**进程内实现**（`eventbus/inproc`、`workflow/local`），中间件属**第 3 层可替换件**。因此允许在 `minimal` 档后置 —— 这让"顺序"从"不可协商"降级为"推荐"，但**推荐理由不变** |

**stack 内顺序**（由 `depends_on: condition: service_healthy` 强制，非人工排）：

```
NATS:      nats-server(启用 JetStream) → 校验 /jsz → 定义 stream/consumer
Temporal:  PG(healthy) → auto-setup(迁移 schema → SERVING) → UI → 建 opic 命名空间
```

## 五、与既有 `opic-deploy`（18 中心版）的对齐与三处校正

既有仓 `/Users/ccoe/Documents/opic/opic-deploy` 的编排（`bin/install.sh` 八阶段 ＋ `stack_registry()` order）**经现场验证有效**，本文的 S0~S3 与 S17 直接沿用其阶段 0~6 与阶段 8 的划分。以下三处在 23 域新体系下需校正：

| # | 发现 | 事实 | 影响 | 建议 |
|:--:|---|---|---|---|
| 1 | **顺序规范有两处定义且互相冲突** | `bin/global/common.sh` 的 `stack_registry()`：`registry=30 < database=40`；`manifests/versions.yaml`：`database=30 < registry=35` | 同一批组件的相对顺序在两处相反，不同脚本读不同源会得到不同顺序 | **收敛为单一事实源**：只保留 `versions.yaml`（组件级）为准，`stack_registry` 由它派生 |
| 2 | **存在逆拓扑**：`asset` 的依赖列写了 `netbox`，但 `asset`（order 60）排在 `netbox`（order 80）**之前** | `docs/guide/DEPLOY.md` §2.1 依赖表 | 属性同步器首次启动时 NetBox 尚未就绪 → 同步失败重试（容器不断，但首轮脏） | **`netbox` 提到 `asset` 之前**；或明确声明为"软依赖、允许首轮失败重试" |
| 3 | **完成横幅的域码口径过时** | `install.sh` 末尾只列 12 个域码（`ztsc arc sys dbs reg harbor ast ign clc usr net infra`） | 与 23 域新体系脱节，新人按横幅找地址会找不到 | 横幅改由 `stack_registry` 动态生成，避免硬编码 |

> 第 1、2 项属**顺序正确性问题**，与本文件主题直接相关；第 3 项属展示口径，顺带记录。

## 六、执行编排

### 6.1 与八阶段编排的对接

| 旧仓阶段 | 本文对应 | 处理 |
|---|---|---|

### 6.2 档位（J7）与阶段的映射

| 档位 | 覆盖阶段 | 效果 |
|---|---|---|
| `minimal` | S0~S9（含 S8 的 NATS） | 平台可登录、可注册能力、事件总线可用 —— **最小可交付里程碑** |
| `standard` | ＋ S10~S13 | 交付链、集群、租户与应用层完整 |
| `full` | ＋ S14~S17 | 流量治理、运营成本、数据与智能资产、合规、观测 |
| 显式开关 | `ENABLE_CERT` / `ENABLE_VPN` / `ENABLE_TEMPORAL` | 不随档位自动启用者，需显式打开（镜像需自备或体量较大） |

### 6.3 启停纪律

```bash
# 启动：按 order 升序
for s in <按 S0..S16 顺序排列的 stack>; do (cd stacks/$s && docker compose up -d); done
# 停止 / 升级 / 回滚：严格逆序
for s in <逆序>; do (cd stacks/$s && docker compose down); done
```

- **回滚优先 `down` 而非 `down -v`**：数据目录为 bind mount，`down -v` 只清匿名卷，**不会**清数据 —— 别误以为"回滚即清空"。
- **升级顺序**：改 `.env` 的 tag → `compose pull` → **逆序 down → 正序 up**（先停上层再停底层，避免上层在底层重建期间持有失效连接）。
