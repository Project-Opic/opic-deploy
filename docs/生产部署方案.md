## 一、一句话结论

**生产形态 = Pigsty 主机级托管数据面（PG 高可用 + Redis，Ansible 幂等安装）＋ docker compose 托管应用面（ZITADEL/Casdoor/NATS/Temporal/Harbor）＋ Traefik TLS 统一入口（域名 + 证书）**；边界判据不变（116 号）：有持久状态且要主机级 HA → Pigsty，无状态或容器化优先 → compose。全流程映射 115 号 S 序，安装编排为 P0~P9（§四）。

## 二、参考拓扑与节点规划

> 拓扑是**参考基准**而非硬性要求——Pigsty 支持单机到任意规模，节点数按现场资源伸缩，角色边界（数据面/应用面分离）必须保持。

### 2.1 节点角色

| 节点 | 角色 | 承载 | 数量（最小/推荐） |
|---|---|---|:--:|
| node-1 | PG 主 | Pigsty PGSQL（primary）＋ etcd ＋ PGBackRest | 1/1 |
| node-2 | PG 备 | Pigsty PGSQL（replica，流复制）＋ etcd | 1/1~2 |
| node-3 | 基础设施 | etcd（仲裁）＋ Pigsty INFRA（Prometheus/Grafana 采集面）＋ 备份存储挂载（NFS/对象网关） | 1/1 |
| node-4 | 应用面 | docker compose 全栈：Traefik、ZITADEL、Casdoor、NATS、Temporal、Harbor | 1/2（keepalived VIP） |

- **最小生产 = 3 节点**（etcd 三副本分布 node-1/2/3；应用面暂与 node-3 合署，标注重载）；**标准 = 4 节点**（应用面独立）。
- Redis 由 Pigsty REDIS 模块部署（随 PGSQL 节点或独立 `redis.yml` 拓扑，v1 建议 1 主 1 复制挂 node-1/2）。

### 2.2 节点基础要求（P0 输入）

| 项 | 要求 |
|---|---|
| 操作系统 | EL 8/9 或 Ubuntu 22/24（Pigsty 4.5 支持矩阵），x86_64 |
| 硬件 | 数据节点：≥8C/32G，数据盘 NVMe/SSD 独立挂 `/data`（≥1T）；应用节点：≥8C/16G，系统盘 ≥200G |
| 网络 | 节点间内网互通（建议万兆或 ≥1G）、统一 VIP（keepalived，浮在 haproxy 前）、出网或离线仓库二选一 |
| 时钟 | chrony 与内网 NTP 源同步（偏差 >100ms 会影响复制与证书） |
| SSH | 管理机（node-3）到全部节点 root 免密（Ansible 前提） |

### 2.3 域名与证书规划（全部走 node-4 Traefik，Harbor 除外）

| 域名（以 `opic.example.com` 为例） | 指向 | 用途 |
|---|---|---|
| `auth.opic.example.com` | node-4:443（Traefik） | ZITADEL（ExternalDomain，**必须与之一致**） |
| `casdoor.opic.example.com` | node-4:443 | Casdoor |
| `nats.opic.example.com` | node-4:443 | NATS monitor（内网解析） |
| `temporal.opic.example.com` | node-4:443 | Temporal UI |
| `harbor.opic.example.com` | node-4:**8443**（Harbor 自管 nginx，TLS） | 镜像仓库（v1 独立证书端口，避免双层代理；v2 可收编 Traefik） |
| 证书 | 通配符 `*.opic.example.com` | 来源二选一：企业 CA / O-CRT 域签发（推荐）；Let's Encrypt 需出网 |

## 三、与 DEV 容器化模式的差异总表

| 维度 | DEV 容器化（117 号实测） | 生产形态（本方案） |
|---|---|---|
| PostgreSQL | `postgres:16-alpine` 单实例容器 | Pigsty PG HA：Patroni + etcd + haproxy(:5433 rw/:5434 ro) + VIP + PGBackRest |
| Redis | `redis:8` 容器 | Pigsty REDIS 模块（主机级） |
| Temporal PG | 栈内独立 PG 容器 | **并入 Pigsty 统一实例**（`temporal`/`temporal_visibility`，116 号 §4.1 收敛选路②） |
| IdP 库 | opic-pg 容器 | Pigsty 实例（库/角色由 `pigsty.yml` 声明式创建，替代 docker init 脚本） |
| 入口 | Traefik :18880，api.insecure=true，nip.io | Traefik **:443 TLS**，api.insecure=false，企业域名 + 通配符证书，http→https 重定向 |
| Harbor | v2.12.2 离线安装器，http :18700 | v2.15.2（在线或离线包），**https :8443** 自管证书 |
| 备份 | 手工 pg_dumpall（手册 §四） | PGBackRest 自动：周全量 + 日增量 + WAL 归档，落 node-3 存储并异地拷贝 |
| 监控 | 手工探针 + 门禁脚本 | Pigsty INFRA 采集面（PG/Redis/节点）保留，聚合告警归 O-MON（第二步） |
| 口令管理 | `.env` 600 | `.env.prod` 600 + age 加密分发 + 离线保管（masterkey 同） |
| 回退 | —（即 fallback 本体） | 可整体回退到容器化模式（数据经 dump/restore 迁移） |

## 四、安装编排（P0~P9）

> 映射 115 号 S 序：P0~P1≈S0/S1，P2~P3=S4（数据基座 Pigsty 形态），P4≈S2/S3，P5=入口（S3 壳），P6=S5，P7=S8，P8=S9，P9=S17 前段。启动正序、停止逆序纪律不变。

| 序 | 步骤 | 要点 | 验收门禁 |
|:--:|---|---|---|
| **P0** | 主机前置 | 系统参数（`vm.overcommit`、透明大页 off、swappiness=1）、防火墙最小端口（§六表）、chrony、数据盘挂 `/data`、SSH 互信、**离线介质分发**（Pigsty offline 包 / Harbor offline tgz / compose 镜像 tar，均放入 node-3 统一目录） | `ansible all -m ping`、`chronyc tracking` 偏差达标、防火墙端口核对脚本通过 |
| **P1** | 凭据与密钥 | 从 `.env.example` 派生 **`.env.prod`**（gen-env.sh 可复用），追加：`PG_ADMIN_PASSWORD`（Pigsty `pg_admin_password`）、Patroni/etcd 口令、各库属主口令、TLS 证书路径、`HARBOR_VERSION=v2.15.2`；证书文件分发 node-4 `/opt/opic/certs/` | `.env.prod`（600）+ 证书就位；age 加密备份一份离线 |
| **P2** | Pigsty 安装（数据面） | node-3 上 `get-pigsty`（离线包）→ 编写 `pigsty.yml`：`nodes[]`=node-1/2/3、`pg_cluster=opic-pg`、`pg_databases[]`=`[opicdb,zitadel,casdoor,temporal,temporal_visibility]`、`pg_users[]`=各业务角色（见 §四.附）、启用 `redis.yml` 拓扑 → `ansible-playbook pigsty.yml` → `ansible-playbook redis.yml` | `patronictl list` 全员 running/primary 唯一；`curl node-VIP:5433`（rw）与 `:5434`（ro）通；VIP ping 通；`redis-cli -h <vip> PING`；`pgbackrest --stanza=pgsql check` 通过 |
| **P3** | 建库授权核对 | Pigsty 已声明式建库建角色；核对：库 5 个、属主角色与 `.env.prod` 口令一致、`pg_hba.conf` 仅放行应用网段（scram-sha-256），禁 `trust` | `psql` 逐库连接验证 + `pg_hba_file_rules` 审计无宽放行 |
| **P4** | 应用节点前置 | node-4 安装 Docker 24+/Compose v2、建 `opic-net`、`/opt/opic/{data,certs}`、离线导入 compose 镜像 tar（ZITADEL/Casdoor/NATS/Temporal/Traefik 五栈，版本口径 = 117 号实测：ZITADEL ghcr v4.19.3、Temporal 1.29.0） | `docker info`、`docker load` 清单核对、DNS 解析五个域名到 node-4 |
| **P5** | Traefik（TLS 入口） | 复用 `stacks/traefik`，生产差异：`TRAEFIK_WEB_PORT=80`、`TRAEFIK_WEBSECURE_PORT=443`、**关闭 `api.insecure`**、追加 `--entrypoints.web.http.redirections.entrypoint.to=websecure`、证书动态文件配置（通配符证书挂 `/opt/opic/certs`） | `https://auth.opic…` 证书链通过；`http://` 301 到 https；dashboard 无未授权访问 |
| **P6** | ZITADEL ＋ Casdoor | 复用 `stacks/zero-trust`/`stacks/casdoor`，生产差异：库 host=node-VIP（haproxy 5433）、`ZITADEL_EXTERNALSECURE=true`、`ZITADEL_DOMAIN=auth.opic…`、`ZITADEL_EXTERNALPORT=443`、Casdoor 走 `casdoor.opic…`（443）；login-client PAT / masterkey 流程同 DEV（volume chown init 容器保留） | healthz 与 login 经 **https 域名** 200；ZITADEL 库在 Pigsty 实例（`\l` 可见且非容器） |
| **P7** | NATS → Temporal | NATS monitor 仅内网 DNS；Temporal：`DB` 指向 Pigsty VIP（库名/口令为 P2 声明值），auto-setup 迁移自身 schema（116 号 §3.2 豁免不变），admin-tools 1.30.4 | `/jsz` 无 error；`operator cluster health` OK；UI 经 https 域名可达 |
| **P8** | Harbor（v2.15.2） | 官方安装器（在线或离线 tgz），`harbor.yml`：`https.port=8443` + 通配符证书、`external_url=https://harbor.opic…`、`data_volume=/opt/opic/harbor/data`（独立盘/NFS）；`HARBOR_ADMIN_PASSWORD` 走 `.env.prod` | `https://harbor.opic…/api/v2.0/health` healthy；`docker login` + push/pull 演练一镜像 |
| **P9** | 验证收口 | 九项生产门禁（表下）＋ **两项演练**：① patroni switchover 主备切换，应用连接无感知（haproxy 重路由 ≤10s）；② pgbackrest 恢复演练（restore 到临时目录 + PITR 校验） | 门禁脚本全绿 + 两项演练记录归档（117 号 verify-step1.sh 改造为生产版：PG 门禁指向 VIP:5433，其余同） |

**§四.附：Pigsty 声明式建库清单（写入 pigsty.yml）**

> **建库规则（用户规则，2026-10-01）**：OPIC 全部能力中心**共用一个数据库实例 `opicdb`，每个能力中心为单独的一个 schema**。第三方引擎（ZITADEL/Casdoor/Temporal）不属能力中心，因引擎限制（ZITADEL/Temporal 要求独占数据库命名空间）保留独立库——此为该规则的**显式边界**，随本方案登记。

| 库 | 内容 | 属主角色 | 消费方 |
|---|---|---|---|
| `opicdb`（唯一业务库） | **23 个中心 schema**（每中心一个）：`osec osys oarc odbs oreg ocrt ovpn oign oclc oosc oadd oast ousr opip oapp ocsc oapf oopr odat omdl oknb omon ocmp`（域码小写） | `opicdb_owner`（组角色；第二步各中心上线时按域发专属登录角色并授权对应 schema） | 23 个能力中心（中心内 migrations/ 纪律不变，禁跨 schema 外键，跨中心只走 API+Event Bus） |
| `zitadel` | 引擎自管 schema | `zitadel` | stacks/zero-trust（运维侧 IdP） |
| `casdoor` | 引擎自管表 | `casdoor` | stacks/casdoor（租户侧 IdP） |
| `temporal` / `temporal_visibility` | 引擎自管 schema | `temporal` | stacks/temporal（standard visibility，无 ES） |

## 五、备份与高可用设计

| 对象 | 策略 | 恢复目标 |
|---|---|---|
| PostgreSQL | PGBackRest：周日全量 + 周中增量 + WAL 连续归档，保留 30 天；备份先落 node-3 本地存储，再同步异地（NFS/对象存储） | RPO ≤ 5 分钟（WAL 归档间隔），RTO ≤ 30 分钟（restore + PITR） |
| PG 高可用 | Patroni 自动 failover（etcd 仲裁）；计划内维护走 `patronictl switchover`（低峰窗口） | 切换 ≤ 10s（haproxy 健康探测间隔内） |
| Redis | 主从 + AOF everysec；随 Pigstu REDIS 模块管理 | 缓存语义，可重建 |
| ZITADEL masterkey | 与 `.env.prod` 同级加密离线保管（**丢失即 ZITADEL 数据作废**） | — |
| Harbor | `/opt/opic/harbor/data` 冷备周度（停机窗口）或外接对象存储 | 镜像可重推，优先保库 |
| 演练 | **月度恢复演练**（pgbackrest restore → PITR 校验）＋ 季度主备切换演练 | 演练记录归档至 ops 台账 |

## 六、安全基线（生产版，上线前逐项核对）

1. **防火墙最小端口**：node-1/2/3 仅放行节点间网段（5433/5434/8008 patroni/2379-2380 etcd/9100-9101 exporter/22 管理网）；node-4 对外仅 80/443/8443，22 限管理网；Pigsty Grafana(3000)/Prometheus(9090) 仅内网。
2. `pg_hba.conf`：仅应用网段 + 管理网段，`scram-sha-256`，禁 `trust`；变更走变更单。
3. Traefik `api.insecure=false`（DEV 坑位结论直接继承）；dashboard 如需开放走 BasicAuth + 内网 ACL。
4. 全站 TLS：五域名证书链校验入月度巡检；证书到期前 30 天告警（O-MON 或 cron）。
5. SSH：key-only、禁 root 密码、fail2ban；管理操作留 `X-Trace-Id` 习惯（平台规则第 8 条审计头）。
6. `.env.prod` 与 masterkey：age 加密存放于堡垒/密码库；**严禁入 git**（`.gitignore` 已排除 `.env*`）。
7. Casdoor/ZITADEL 管理员首登改密并轮换；Harbor admin 同。

## 七、监控与告警衔接

- **采集面**：Pigsty INFRA 自带 Prometheus/Grafana（PG/PGPool/Redis/节点 exporter），保留为本机采集（116 号 §三决策 5）。
- **聚合面**：O-MON（第二步）联邦采集上述 Prometheus；第一步期间用 Pigsty 内置告警最小集：复制延迟 >10s、WAL 堆积、磁盘 >85%、连接数 >80%、backup 失败、证书到期不足 30 天。
- **门禁巡检**：verify 脚本（生产版）进 crontab 每小时，异常 `wall` + 消息通道。

## 八、升级与回退

| 场景 | 流程 | 回退 |
|---|---|---|
| Pigsty 小版本 | 先 pgbackrest 全量 → ansible playbook 升级（先 replica 后 primary，switchover 滚动） | 按库 dump + 旧版本重装回退；或 PITR |
| PG 小版本 | 同上滚动：switchover → 升 replica → 提主 → 升旧主 | Patroni 回切 |
| 应用面（compose） | 改 `.env.prod` tag → `pull` → **逆序 down → 正序 up**（115 号 §6.3） | tag 回退重部署 |
| 整体回退容器化模式 |DEV 形态即 fallback：应用栈指回容器 PG（dump/restore 迁移） | 116 号 §五 |

## 九、与 116/117 的关系

- 116 号 §三决策 1（两分法）在本方案完整落地；§4.1 决策（Temporal 并库）随 P2 声明式建库一并关闭。
- 117 号 DEV 实测结论**继续适用**于生产应用面：traefik label 挂目标容器、zitadel 不设 healthcheck（post-install 门禁）、init-perms 卷属主、casdoor `dbName` 与去 `--createDatabase`、nats 无服务器级 `max_streams`、镜像 tag 前缀（ghcr 带 v）与 `--platform linux/amd64` 搬运。
- 数据迁移（DEV → 生产，如需）：dumpall 全量 + 角色口令对齐 `.env.prod`；不做在线复制。
