## 一、一句话结论

**第一步把 8 项基础设施装到「可用」而不是「能跑」：数据面（PG 高可用 + Redis）由 Pigsty 主机级托管，应用面（ZITADEL / Casdoor / NATS / Temporal / Harbor / Traefik）由 docker compose 托管；边界判据是「有无持久状态、要不要主机级 HA」。**

全部 8 项落在 115 号顺序表的 **S0~S5 ＋ S8 ＋ S9 ＋ Traefik 壳** 区间内，不改变 115 号的拓扑判据（J1~J7）；语义中心（O-SYS / O-ARC，S6~S7）及之后的能力中心属**第二步**。

## 三、五项决策点处置（本轮收敛）

| # | 决策点 | 处置 | 理由 |
|:--:|---|---|---|
| 1 | **Pigsty vs compose 裸 PG** | Pigsty 托管**数据面**：PG 高可用集群（Patroni + etcd + haproxy/vip）＋ Redis；compose 托管**应用面**。115 号 §4.1 的「Temporal 独立 PG vs 并库」决策点就此收敛为**并库**：`temporal` / `temporal_visibility` 两库由 Pigsty 建库授权，独立实例退役为 fallback | 数据面要 HA 与主机级备份（PGBackRest），主机级 Ansible 是 Pigsty 的强项；应用面保持容器化，演进与回滚不受主机束缚 |
| 2 | **Traefik vs nginx** | 收敛为 **Traefik 单一入口**，既有 nginx 入口编排退役；Traefik 壳在镜像就绪后（F3）即起，路由靠 docker label 服务发现、随各栈启动自动出现，S17 全局收口改为 Traefik 验证 | 与容器生态集成好、自动证书（Let's Encrypt/自签 CA 皆可）；路由依赖 O-SYS 能力注册的部分本就该晚于 S6，壳与路由两段式正好承接 J6（幂等先做、可见后做） |
| 3 | **Redis 供给方** | 实例由 **Pigsty Redis 模块**部署（与 PG 同为数据面主机级组件）；治理面（凭据发放、配额、淘汰策略）登记为 **`O-DBS` 域决策点**，随第二步收敛 | J3 面分离：实例无业务语义可先于身份中心；Pigsty 原生支持 Redis，不引入第四种安装范式 |
| 4 | **Casdoor 入序** | 与 ZITADEL 同置 **S5**（O-SEC 承载双 IdP）；授权链不变：Casbin RBAC 优先 → 拒绝则查 ZITADEL/Casdoor → 任一通过即允许 | 平台规则第 9 条早已确立「运维侧 ZITADEL、租户侧 Casdoor」分工，115 号 v1.0 漏列，本轮补齐 |
| 5 | **Pigsty 自带监控 vs O-MON** | Pigsty 监控栈（Prometheus/Grafana）保留为**本机采集面**；聚合、告警规则、通知仍归 **O-MON（S17）** | 呼应 J5「观测两段式」：采集早准备、聚合晚收口，避免两套聚合面打架 |

### 3.1 版本基准

- **Pigsty 4.5**（2026-10-01 官网核实）：支持 PG 12~18 共 12 个内核分支，默认 PG 18；模块含 PGSQL / ETCD / MINIO / **REDIS** / Docker / JuiceFS 等；Ansible 幂等剧本安装，Linux-native（不依赖 K8s/Docker），EL 8/9/10、Ubuntu 22/24/26、Debian 12/13，x86_64 / Arm64。满足平台纪律「PostgreSQL 16+」。
- 其余 7 项版本以 `manifests/versions.yaml` 为**单一事实源**登记（呼应 115 号 §五校正 1），本文不重复维护版本号。

### 3.2 平台纪律豁免登记（AutoMigrate）

平台纪律「禁止 AutoMigrate」约束**业务中心的业务库**；ZITADEL / Casdoor / Temporal / Harbor 为第三方引擎，各自管理自身 schema（ZITADEL 内置迁移、Temporal 走 `auto-setup`）。本步登记**豁免**：第三方引擎自管 schema，业务中心仍严禁；Temporal 库虽并入 Pigsty 统一实例，其库内 schema 仍由 Temporal 自管（建库授权与 schema 管理分离）。

## 四、第一步执行序（F0~F8）

> 对应 115 号 S 序，启动正序、停止逆序；每步有验收门禁，门禁不过不进下一步。

| 序 | 内容 | 对应 S | 要点与验收门禁 |
|:--:|---|:--:|---|
| **F0** | 主机与运行时准备 | S0 | Docker 24+ / Compose v2、`yq`、`opic-net`、时钟同步；**Pigsty 前置**：Linux 主机（EL/Ubuntu/Debian）、节点间 SSH 互信、Ansible 就绪。门禁：`docker info`、`ansible all -m ping` |
| **F1** | 凭据与密钥 | S1 | 生成 PG admin 口令、JWT、NATS、Temporal PG 账号等，落 `.env.runtime`（600）。**在全部 compose 之前**（115 号 S1 纪律不变） |
| **F2** | 宿主初始化 | S2 | `init-volumes` → `init-hosts` → `init-certs` → `init-nfs`；Traefik 证书目录在此建好 |
| **F3** | 镜像准备 ＋ **Traefik 壳** | S3 | 离线导入 / 在线拉取 8 项镜像；`traefik` 栈起壳（80/443 + dashboard），此时无路由属预期。门禁：`traefik /ping` 返回 200 |
| **F4** | **Pigsty：PG HA ＋ Redis** | S4 | `get-pigsty` → `configure` → Ansible 剧本（`deploy.yml`）；etcd（共识）→ Patroni（HA）→ haproxy/vip → PGBackRest（备份）→ Redis 模块。门禁：`pg_isready`（haproxy 5433 主库）、`patronictl list` 全员 running、`redis-cli PING`。**建库授权**：`opicdb` schema 前缀规划 + `temporal` / `temporal_visibility` + ZITADEL/Casdoor/Harbor 各自库 |
| **F5** | **ZITADEL ＋ Casdoor（双 IdP）** | S5 | ZITADEL（运维侧，8080）＋ Casdoor（租户侧，8000），库指向 F4 的 PG。门禁：ZITADEL `/debug/healthz` ok；Casdoor 登录页 200 |
| **F6** | **NATS → Temporal** | S8 | NATS（4222 / monitor 8222，启用 JetStream）先起（零依赖，最快可验证）；Temporal（frontend 7233）后起，`auto-setup` 迁移自身 schema（§3.2 豁免）。门禁：NATS `/jsz` 正常、stream/consumer 就绪（语义注册留第二步随 O-SYS 补登）；Temporal 命名空间 `opic` 建立且 SERVING |
| **F7** | **Harbor** | S9 | `registry` 栈（O-REG），后端存储可接 F4 的对象存储或 NFS。门禁：`/api/v2.0/health` 返回 healthy |
| **F8** | 第一步验证收口 | S17（前段） | 八项健康门禁全绿 + 入口连通性走查（经 Traefik 到达 ZITADEL/Casdoor/Harbor 控制台）；观测聚合与全量 `verify` 仍留 115 号 S17 全局收口（依赖第二步的中心） |

**第一步与第二步的交接物**：可用 PG 集群与建库台账、双 IdP 可登录、事件总线与流程引擎运行时就绪、镜像仓可推送、统一入口壳在线。第二步（O-SYS / O-ARC 起）接手语义注册：能力注册、`EventType`/`EventSubscription` 语义、Traefik 路由随中心栈自动发现、O-MON 聚合收口。

## 五、风险与回退

| 风险 | 处置 |
|---|---|
| Pigsty 主机级安装与既有 compose 编排范式冲突 | 边界已二分（§一/§三决策 1）；`stacks/database`（compose 裸 PG）**保留为 minimal 档 fallback**，标记 deprecated，仅离线应急用 |
| 离线环境无法访问 Pigsty 软件仓 | Pigsty 支持离线安装（软件仓打包随发行版提供）；F3 镜像导入纪律（尽早暴露下载失败）同理适用于 F4 的系统包 |
| Temporal `auto-setup` 与统一实例的 schema 管控张力 | §3.2 已登记豁免：库归 Pigsty、库内 schema 归 Temporal 自管；O-DBS 只管建库授权与备份策略，不碰其 schema |
| 双 IdP 配置漂移 | ZITADEL/Casdoor 均以配置文件 + 环境变量声明式管理，纳入 `.env.runtime` 与 stack 钩子纪律，禁止手工点选后不落盘 |
| Traefik 壳先起导致「无路由」误判为故障 | F3 门禁只验 `/ping`；路由为空属预期，F8 建立入口连通性基线 |
